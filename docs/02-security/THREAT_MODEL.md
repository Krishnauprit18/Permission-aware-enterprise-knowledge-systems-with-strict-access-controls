# Threat Model

- Phase: P01
- Scope: the local-only Permission-Aware Enterprise Knowledge System and its synthetic Northstar data flows
- Method: asset and trust-boundary analysis, STRIDE, and LLM/RAG abuse-case analysis
- Status: baseline threat model; implementation-specific controls and residual risk require later review

## 1. Assets and security objectives

The primary assets are identity and session state; tenant/account relationships; roles, grants, and policy versions; raw source resources and attachments; revisions, chunks, metadata, embeddings, indexes, and caches; evidence packages, answers, citations, and external exports; prompt instructions and model inputs/outputs; source credentials and configuration; migrations, dependencies, build artifacts, and provenance; and audit traces, backups, and recovery data.

The system must preserve confidentiality, integrity, availability, accountability, tenant isolation, authorization freshness, deletion correctness, citation correctness, and grounded output. The highest-severity failure is protected content reaching an unauthorized principal or an LLM context.

## 2. Actors

- Unauthenticated requester or stolen-session attacker.
- Authenticated but curious or malicious employee.
- Cross-tenant user attempting to use an account or tenant hint as a grant.
- Privileged tenant administrator or operator.
- Source owner, connector worker, parser, indexer, and cache worker.
- Malicious source author, message participant, attachment author, or compromised source system.
- Local model process or model provider boundary, treated as untrusted for authorization.
- Dependency, model-artifact, build, or registry attacker.
- External recipient who receives a customer-safe answer.

## 3. Entry points

- Interactive query and authenticated session endpoints.
- Audience selection, answer export, citation display, and trace lookup.
- Administrative identity, role, account relationship, grant, policy, and deletion actions.
- Source connector configuration, synchronization, webhook/update events, and source credentials.
- File and attachment ingestion, transcript/document parsing, and metadata normalization.
- Lexical/semantic search, reranking, evidence resolution, model adapter, and answer validation interfaces.
- Local configuration, migrations, dependency manifests, build inputs, backups, and restore operations.
- Logs, metrics, traces, caches, generated reports, and operator tooling.

## 4. Protected flows

1. A client query crosses the application boundary and is bound to an authenticated principal and server-resolved tenant.
2. Current policy state determines view scope and, separately, external-share scope.
3. Source revisions cross the connector boundary into validated canonical resources and lineage-bearing derivatives.
4. Search produces candidates only within tenant/account scope; current authorization filters before ranking and model-facing processing.
5. Authorized evidence is resolved for authority, freshness, conflict, and sufficiency.
6. A model receives only the authorized evidence package plus system-controlled task instructions; source text remains untrusted data.
7. Output validation maps claims to supplied evidence IDs and applies audience/share policy before release.
8. Updates, revocations, deletion events, logs, caches, backups, and dependencies cross their respective trust boundaries with integrity and minimization controls.

## 5. Threat register

Risk labels are initial prioritization only: `Critical` means a direct protected-data or authorization failure; `High` means material integrity, availability, or disclosure impact; `Medium` means a bounded supporting failure. Each row names a planned regression or verification test. A test is not implemented by this phase.

| ID | Category | Threat and affected assets/boundary | Required mitigation | Planned verification |
|---|---|---|---|---|
| T-01 | STRIDE: Spoofing / auth failure | Stolen, forged, replayed, expired, or confused session claims impersonate a Northstar user or cross tenant. Affects identity, tenant scope, queries, exports, and traces at TB-1/TB-2. `Critical` | Authenticate every protected request; bind principal and tenant server-side; reject invalid, expired, replayed, or ambiguous claims; use least privilege and auditable privileged access. | Test invalid/expired/replayed/tampered sessions, missing tenant binding, and cross-tenant attempts; assert no evidence or trace contents are returned. |
| T-02 | STRIDE: Tampering | A client, source, worker, or compromised store changes `tenant_id`, account, department, classification, ACL, revision, deletion state, or lineage. Affects policy integrity and search derivatives at TB-3/TB-4. `Critical` | Validate and integrity-protect security metadata; separate source content from policy authority; reject inconsistent lineage; fail closed when metadata integrity or freshness is uncertain. | Mutate each security field in fixtures and storage boundaries; assert rejection or deny, no index eligibility, and an auditable integrity failure. |
| T-03 | STRIDE: Repudiation | A privileged role change, share, deletion, or answer cannot be attributed or reconstructed. Affects auditability at TB-8. `High` | Emit structured audit events with principal, action, target ID, policy version, outcome, correlation ID, and time; protect event integrity and restrict access; minimize payloads. | Perform each privileged and answer-path action; assert trace presence, stable identifiers, outcome, and no raw restricted content. |
| T-04 | STRIDE: Information disclosure / broken access control | Unauthorized chunks enter candidate results, reranking, citation construction, logs, caches, or LLM context; account or tenant scope is bypassed. Affects all content at TB-2/TB-5/TB-6. `Critical` | Enforce current authorization before downstream model-facing processing; deny by default; apply tenant and account constraints at every retrieval path; never use answer filtering as authorization. | Instrument the full query path with canary chunks for every classification, account, and tenant; assert unauthorized IDs never reach reranker, evidence package, citations, model adapter, cache, or answer. |
| T-05 | STRIDE: Denial of service | Oversized queries, result fan-out, parser bombs, attachment decompression, source floods, or repeated model work exhaust local resources. Affects availability and may pressure operators to bypass controls. `High` | Bound input size, parsing depth, result counts, concurrency, time, memory, and model work; rate-limit by principal; backpressure and fail closed when limits or dependencies fail. | Send boundary-size, decompression, high-concurrency, slow-source, and repeated-query fixtures; assert bounded resource use, safe errors, and no policy bypass. |
| T-06 | STRIDE: Elevation of privilege | Role/department/account relationship confusion lets an Account Manager access Legal, Finance, another account, or a revoked relationship. Affects ACLs and evidence at TB-2/TB-5. `Critical` | Centralize deterministic policy evaluation; model role, department, account, grants, classification, tenant, and policy version explicitly; test separation of duties; no LLM authorization. | Execute an authorization matrix for every persona, department, classification, tenant, account, and revoked relationship; assert least privilege and fail-closed ambiguity. |
| T-07 | STRIDE: Injection | User questions, source text, metadata, citations, or attachments reach query languages, templates, commands, renderers, or policy expressions as executable syntax. Affects stores and processing at TB-1/TB-3/TB-4/TB-7. `High` | Use typed boundaries, parameterized queries, safe template handling, context-aware output encoding, allowlists, and parser isolation; never interpret source text as policy. | Fuzz query, metadata, markup, delimiter, and citation fields with injection payloads; assert data-only behavior, safe rendering, and unchanged authorization. |
| T-08 | LLM/RAG: indirect prompt injection | A Slack message, transcript, document, or attachment instructs the model to ignore system rules, reveal restricted material, or cite itself as authoritative. Affects instructions and model context at TB-3/TB-6. `Critical` | Label retrieved text as untrusted data; keep instructions outside evidence; do not grant tools or authorization to the model; validate claims/citations after generation; refusal on compromised evidence. | Seed authorized injection text and inaccessible decoy content; assert no policy change, no decoy in context/output, no invented citation, and safe refusal or grounded answer. |
| T-09 | LLM/RAG: data poisoning | Malicious or stale source edits manipulate authority, freshness, ranking, conflict resolution, or answer content. Affects provenance, indexes, evidence, and answers at TB-3/TB-4/TB-5. `High` | Preserve source/revision lineage, effective and update times, source authority metadata, deletion state, and conflict markers; use anomaly checks and explicit refusal/qualification rules. | Insert contradictory, backdated, superseding, and high-similarity poisoned records; assert deterministic authority/freshness handling and separate retrieval/generation failures. |
| T-10 | LLM/RAG: sensitive information disclosure | Answer text, citations, refusal details, exports, model outputs, or side channels disclose restricted or customer-confidential information to a viewer or external audience. Affects evidence/output at TB-6/TB-7/TB-8. `Critical` | Apply `can_view` before evidence assembly and `can_share_externally` for the named audience; validate claims and citations; redact or refuse; use generic refusal wording and minimize observable details. | Test unauthorized, customer-safe, restricted, and mixed-classification prompts; assert no sensitive claim, citation, identifier, count, or raw content crosses the audience boundary. |
| T-11 | Supply chain / dependency compromise | A parser, search library, model artifact, package, or transitive dependency is malicious, vulnerable, or replaced. Affects code, model behavior, source content, and build at TB-9. `High` | Pin dependencies and lockfiles; review changes; generate an SBOM; scan dependencies and artifacts; verify checksums/signatures/provenance where available; isolate high-risk parsers and model assets. | Build from a controlled manifest, inject a changed dependency/artifact, and assert verification or gate failure; record SBOM and provenance evidence. |
| T-12 | Logging leakage | Raw chunks, prompts, model output, credentials, policy details, or protected identifiers are copied into logs, traces, metrics, crash reports, or debug output. Affects observability and backups at TB-8. `Critical` | Structured allowlisted events; redaction and minimization before emission; secret scanning; separate operator authorization; never log raw model context or restricted content by default. | Use synthetic secret and classification canaries through success/failure paths; scan logs and traces; assert only stable IDs/reason codes and approved fields remain. |
| T-13 | SSRF / unsafe file parser | A source URL, document reference, image, archive, or parser feature causes arbitrary local/network access, resource reads, code execution, or credential exposure. Affects connectors and parsers at TB-3/TB-4. `Critical` | Explicit source allowlists and network policy; reject arbitrary fetch targets; isolate parsers; bound size, depth, time, and memory; treat file names, URLs, and MIME claims as untrusted. | Test loopback/private targets, redirects, alternate encodings, archive bombs, malformed files, parser crashes, and credential-path references; assert no unauthorized fetch or file read. |
| T-14 | Malicious attachment | A ticket or transcript attachment contains malware, active content, hidden prompt injection, polyglot data, or a decompression bomb. Affects raw/derived content and model context at TB-3/TB-4/TB-6. `High` | Quarantine and type-check attachments; parse only supported safe forms; strip active content where applicable; retain provenance; scan and bound processing; exclude unsafe content from evidence. | Upload synthetic malicious, oversized, polyglot, and prompt-injection attachments; assert quarantine/deny, bounded processing, and no unsafe derivative or model exposure. |
| T-15 | Cache leakage | A cache key omits tenant, account, audience, policy version, revision, or deletion state and returns another user's result or stale protected evidence. Affects retrieval/answer caches at TB-5/TB-7/TB-8. `Critical` | Make cache scope and invalidation security properties; bind keys to effective policy context and audience; invalidate on ACL, deletion, and source revision changes; fail closed on uncertainty. | Warm caches as one persona, revoke or switch tenant/account/audience, delete content, and query as another; assert no prior evidence or answer is returned. |
| T-16 | Timing/existence leakage | Different errors, counts, citations, latency, cache behavior, or refusal wording reveal that an inaccessible resource, account, or policy exists. Affects refusal and observable side channels at TB-1/TB-7/TB-8. `High` | Use generic refusal/insufficient-evidence responses; do not expose protected identifiers, counts, or classification; normalize decision paths where practical; document and test an acceptable observable-difference budget. | Probe existing, inaccessible, deleted, and nonexistent resources across repeated runs; assert no resource identifiers or existence-specific wording and bounded measurable differences. |
| T-17 | Build/source provenance failure | An unreviewed source revision, build parameter, generated artifact, or deployment package cannot be connected to its origin, allowing tampering or irreproducible release. Affects source/build integrity at TB-9. `High` | Record source revision, dependencies, builder/process identity, parameters, artifact digest, and review/change evidence; verify provenance before release and preserve it with the artifact. | Rebuild and provenance-verification fixture; alter source, dependency, or build input; assert mismatch blocks release or is visible as a failed verification. |
| T-18 | Stale authorization or deletion | Revoked roles, removed account relationships, source deletion, or de-permissioning leave searchable chunks, embeddings, citations, or cached answers usable. Affects lifecycle state at TB-2/TB-4/TB-5/TB-7. `Critical` | Check current policy on every authorized query; define bounded ACL invalidation; process deletion tombstones; cascade invalidation to derivatives and caches; do not require re-embedding for ACL change. | Revoke, de-permission, and delete while content remains indexed; query immediately and after the bound; assert no protected ID reaches model-facing flow and no re-embedding is required for ACL-only change. |
| T-19 | Vector/embedding weakness | Semantic retrieval, embeddings, similarity scores, or exported vectors leak or surface content outside current policy, or ranking causes unauthorized content to be considered. Affects derived indexes at TB-4/TB-5. `Critical` | Treat embeddings as sensitive derivatives; bind them to tenant/resource lineage; enforce authorization independently of vector search; restrict export/probing; never use similarity as a grant. | Probe cross-tenant and revoked vectors, nearest-neighbor paths, and export interfaces; assert no unauthorized candidate or vector-derived citation is exposed. |
| T-20 | Improper model output handling | The model emits fabricated citations, executable markup/code, hidden instructions, sensitive fragments, or malformed structured output that downstream code trusts. Affects answer/export at TB-6/TB-7. `High` | Treat model output as untrusted; parse strict schemas; allowlist supported output; validate claims and evidence IDs; encode rendered content; refuse malformed or unsupported output. | Supply malformed, fabricated-ID, HTML/script, code, and sensitive-output fixtures; assert rejection, safe encoding, or refusal and no downstream execution. |
| T-21 | Citation/evidence spoofing | A user or model invents an evidence ID, alters a citation span, or cites an inaccessible/superseded resource. Affects grounding and audit at TB-5/TB-7. `Critical` | Server creates evidence IDs; citation validator accepts only IDs and spans in the authorized supplied evidence package; retain revision and policy context; reject unknown or stale references. | Mutate IDs, spans, revisions, and access state after retrieval; assert validation failure and no citation or answer claim using the invalid evidence. |

## 6. Required security test themes

Later implementation phases must provide regression coverage for pre-context authorization, tenant/account isolation, role and relationship changes, deletion, cache invalidation, refusal non-disclosure, indirect injection, source poisoning, parser/attachment safety, output/citation validation, log redaction, side-channel exposure, dependency/provenance verification, and resource bounds. Security tests must observe every model-facing boundary rather than checking only the final answer.

## 7. Review triggers

Revisit this model when a new source type, external integration, model capability, tool, cache, export path, identity source, parser, deployment mode, or data classification is introduced; when a security finding changes trust assumptions; or when a required standard version changes. No new trust boundary may be accepted implicitly.
