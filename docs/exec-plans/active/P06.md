# P06: Fine-Grained Authorization with OpenFGA

## Objective

Implement the first-class backend authorization boundary using OpenFGA as the
relationship decision source. Keep retrieval, indexing, model calls, and answer
generation out of scope.

## Scope

- Define typed authorization decisions, scopes, resource metadata, and audit
  fields.
- Implement an OpenFGA HTTP adapter for `check` and `list-objects`.
- Enforce tenant membership and server-owned resource metadata before an allow
  can be returned.
- Support tenant, group, department, account, project, resource, direct viewer,
  owner, restricted/legal viewer, `can_view`, and separate
  `can_share_externally` relationships.
- Add deterministic local OpenFGA model and tuple bootstrap.
- Add focused authorization tests and a reusable permission matrix fixture.
- Update architecture/security/state documentation and the prompt archive.

## Security decisions

- OpenFGA is authoritative for relationships, but the application remains the
  policy enforcement point for tenant, lifecycle, classification, and scope
  checks.
- Client claims, client ACL filters, search metadata, and LLM output cannot
  grant access. The adapter uses the validated principal subject only; group
  claims are not treated as authorization tuples.
- Unknown resources, tenant mismatches, unsupported relations, OpenFGA errors,
  and timeouts return deny/indeterminate and never allow protected content.
- Restricted resources require an explicit restricted/legal relation instead of
  inherited account or department access.
- Authorization model version, tuple version, policy version, and a keyed
  request-safe decision fingerprint are returned as audit metadata and are
  designed to bind future cache entries.

## Exit gate

- Authorization unit/integration/security tests pass, including tenant and
  failure-closed matrices.
- Local OpenFGA model and deterministic tuple bootstrap succeed without secrets.
- `can_view` and `can_share_externally` remain separate decisions.
- No retrieval or model-facing feature is implemented.
- Required docs/state ledgers are updated, the sanitized prompt is archived,
  this plan moves to `docs/exec-plans/completed/P06.md`, and checkpoint commits
  are pushed to `origin/master`.
